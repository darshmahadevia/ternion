# Local API measurements, October 25, 2026

Five measured fresh three-node clusters on an Apple M4 Mac with 10 cores, 16 GiB RAM, and macOS 27.0.1. Each trial completed 1,000 durable SETs and 1,500 value-checked linearizable GETs with eight concurrent workers and 1 KiB values. All 12,500 measured public operations completed without a terminal client error or payload mismatch.

| Operation | Median throughput across runs | Run range | Median run p99 | Run p99 range |
| --- | ---: | ---: | ---: | ---: |
| SET | 145.1 ops/s | 131.3 to 189.9 ops/s | 84.22 ms | 71.33 to 90.11 ms |
| GET | 2,936.7 ops/s | 2,754.4 to 2,960.2 ops/s | 5.27 ms | 4.67 to 6.06 ms |

## Method and correctness

The runner builds on the ordinary public client and normal `File.Sync` WAL path. Each cluster uses three independent processes and separate fresh data directories on the same Mac's local APFS storage. It warms the cluster with 20 SETs and 20 GETs before timing. After warmup, it discovers the leader from proposal counters and orders that leader first in the client address list. The client opens a new gRPC connection per operation. Those transport costs remain inside the measurement.

The benchmark now compares every returned GET payload with the written bytes. Public errors or mismatches abort the run. The report retains operation latency arrays, binary hashes, source revision and benchmark patch, workload durations, host load, per-process counters, and before/after metrics. All measured latency sample counts match operation counts. Across the five primary workloads, protocol-counter deltas recorded 5,080 proposals, including session operations, and 11,013 WAL syncs. RPC errors, client errors, and client retry counters each remained at zero. Published p99 values are medians of five per-run p99 values, not a pooled p99.

## Interpretation and limits

These are short local API observations under the recorded background load, not maximum capacity, a production service target, or a measured speedup. SET phases lasted 5.27 to 7.61 seconds and GET phases lasted 0.507 to 0.545 seconds. In particular, the read measurement is a short burst, not a sustained load test. Other user applications and macOS services remained running. All nodes share one host and storage device. SETs include WAL synchronization and GETs include a fresh quorum. They do not measure the same work.

Discovery runs with random leader placement and a fixed first client endpoint mixed direct requests with redirected requests. They were excluded. Three discovery runs completed, and a fourth was deliberately stopped. A subsequent five-run 25,000-operation workload is also retained separately under `results/macos-m4-long-workload-2026-10-25`. It completed, but its fifth run had a large latency outlier and a local connection probe failed with EADDRNOTAVAIL during that workload. The client opens a new TCP connection per operation. Those longer runs are not the source of the primary table. The final five shorter runs use the consistent leader-first setup described above and report all their ranges. They must not be compared as a regression against the earlier Windows result, which used a different machine, smaller workload, and unrecorded leader placement.

An additional 500-SET, 1,000-GET profiling run is excluded from the table. Its native thread samples and process counters are retained under `results/macos-m4-2026-10-25/profile`. Samples document observed waiting and work. No percentage attribution or universal bottleneck is claimed.

## Reproduce

```sh
go build -o .benchmark-work/ternion ./cmd/ternion
go build -o .benchmark-work/ternionbench ./cmd/ternionbench
python3 benchmark/repeat.py --output benchmark/results/my-mac-run --profile
```

Use a fresh output directory. The runner terminates its own processes and removes only its temporary cluster data.
